Data della verifica: 2026-10-20. Ambiente: **solo locale**. Nessun deploy, nessuna risorsa Cloudflare remota, nessuna
credenziale, telemetria di Wrangler disattivata (`WRANGLER_SEND_METRICS=false`).

## Differenze osservate tra SQLite via Node e D1 (locale)
| Aspetto | SQLite (`node:sqlite`) | D1 locale | Impatto sul nucleo |
|---|---|---|---|
| Transazioni | `BEGIN/COMMIT` dall'adattatore | solo `batch()` (transazione implicita) | nessuno: il nucleo usa solo batch atomici |
| `PRAGMA integrity_check` | disponibile | **non autorizzato** | i test usano `quick_check` + `foreign_key_check` su entrambi |
| `PRAGMA journal_mode`, `sqlite_version()` | disponibili | **non autorizzati** | non usati dal nucleo su D1 |
| Chiavi esterne | attivate dall'adattatore | sempre attive | nessuno |
| `sqlite_master` | solo oggetti propri | anche `_cf_METADATA` (dopo la prima scrittura) | le query del nucleo filtrano per nome |
| Errori | messaggio SQLite | prefisso `D1_ERROR:` + messaggio SQLite | il riconoscimento dei conflitti cerca il nome del vincolo: funziona su entrambi |
| Parametri per istruzione | fino a 32766 | **100** | importatore gia' a blocchi da 90; l'adattatore rifiuta oltre 100 con messaggio chiaro |
| Profondita' delle espressioni | 1000 | 100 | nessuna query del nucleo vi si avvicina |
| Ambiente JS | Node | workerd espone comunque un `process` globale anche senza `nodejs_compat` | il nucleo non lo usa (test di portabilita') |

Nessuna differenza ha richiesto di modificare vincoli, trigger o test del nucleo.

## Migrazioni sul D1: decisione presa (2026-10-21)
Strategia **ibrida**: file SQL per `wrangler d1 migrations apply` generati da `MIGRATIONS`, con guardie di versione e
checksum dentro ogni file, stesso registro `schema_migrations` del runner e verifica dello schema. Dettagli, tabella
dei controlli garantiti e procedure: [migrazioni-d1.md](migrazioni-d1.md). Verificata solo in locale.

## Cosa NON e' stato verificato
- D1 **remoto** (produzione): nessun database creato, nessun deploy. Il comportamento remoto (latenza, limiti di
  dimensione del batch e di durata, repliche di lettura, Time Travel) resta da verificare.
- Limiti del piano gratuito e **costi** reali: non misurati (nessun uso remoto).
- Dimensione massima di un batch su D1 remoto per importazioni grandi (migliaia di righe): non misurata.
- Comportamento con piu' Worker concorrenti sullo stesso database remoto (la guardia `write_seq` e' verificata solo
  con richieste sequenziali in locale).
- `wrangler d1 migrations apply --remote`: non provato (provato solo `--local`, vedi [migrazioni-d1.md](migrazioni-d1.md)).
